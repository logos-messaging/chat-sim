Simulations

tools/sim runs a group the way a scenario file says. On master it runs every member in one process: harness-run seats them in one group of logos-chat clients and does the steps on a virtual clock. On Linux a scenario and its seed give the same run every time, which makes it the reference a change to logos-chat is held to. tools/sim then has the fork report read the members’ log, and holds the report against what the scenario expects. It can also run a chat-cli process for each member, and chat-cli is on the local-network branch (see chat-cli and the local-network branch).

A first run

Section titled “A first run”

The flake’s app groupv2-simulation builds harness-run from the checkout and runs tools/sim with it, as --one-process; what follows -- is the sim’s command line. Without Nix:

  • The head says how far the virtual clock went and how long that took, the seed, the verdict, how many members are at the tip, and whether the report is as expected. Every other time is on the clock.
  • member is each member: its installation id, and how many frames it rejected (errors). When any member rejected one, an inbound error table follows: each error in the core’s words, how many frames it was given for, and by how many members.
  • batch is each /add: how many joined, the group’s size after it, and the seconds from the first try of the add until every member waited on held the new roster.
  • post is each post: how many read it, and how long they took.

--out must not exist. It holds plan.json (what the runner was given), group.log and result.json (what it left), runner.out and runner.stderr, report.txt and report.json (the fork report), expect.json (what the report was held to), run.txt (what was printed) and run.json (the same and more, for scripts).

ExitWhen
0every step was done and the report is as the scenario expects
1a step was not done, or the report differs
2the command line or the scenario is refused; nothing started
128 + nsignal n interrupted it; the run is not checked

A run is judged by the check, not by the report’s own exit status: a scenario may expect a verdict other than whole.

A scenario

Section titled “A scenario”

Members are named saro, raya, pax, mira, kes, tomo, then peer7 on. saro creates the group. This one, saved as four.json, seats the others two at a time, has every member lose 2% of the frames it receives and hold the rest for 40 ms, and has every member post:

With network, each member receives through a model of a lossy network: the member table counts the frames that arrived at its model and those the model passed, held at the end and lost. A frame the model loses never comes to its member later, so a wait that a lost frame leaves open runs to the end of its budget, which is why four.json sets 33 s in place of 180.

Sweeps

Section titled “Sweeps”

sweep does a scenario --runs K times and prints a row as each ends. Run k takes the seed seed + k - 1, and so it does with the seed of network. The row names each seed: seed, and network seed.

In run 3 Raya’s model lost two frames, and Raya stayed at epoch 1: it never held the roster that seats Mira. A run that went otherwise names its first difference from the expectation in the check column, and what stopped the steps. Each run keeps its own directory under --out, and sweep.txt and sweep.json hold the rows.

Held to what is expected

Section titled “Held to what is expected”

A run in one process is the same run every time from its seeds, on Linux, so a run that comes out other than it did was changed by a revision of logos-chat or of chat-sim. compare holds each run of a sweep in one process to the outcome a file expects of it: the seeds, the ids of the group and of its members, the verdict, the members at the tip, the seconds of the clock, how the run came out and what stopped its steps, and of a grow step the trunk’s epoch, how the step ended (whole, behind, split, or stalled where the trunk stopped short of the epoch it grew toward), the lines off the trunk, the members off it (behind at the end, on another line, or never joined), and how many of those never joined. A run that came out otherwise has the outcome expected under it, as was, and its change says where the run stands against it.

A run of a grow step stands, highest first, by the epochs without a fork (the first split’s epoch, or the trunk’s where there is none); at the same epochs, whole at the end over any other ending; then the fewer lines off the trunk; then the fewer members off it. Any other run stands by its verdict: a split, the later the better, then any other verdict, then whole, and at each the more members at the tip. A run with no verdict stands lowest.

ChangeMeans
samethe outcome is the one expected
betterthe run stands higher than the one expected
worsethe run stands lower
re-rolledboth runs drew ids, and the run drew others than the one expected, the group’s or the members’ (a run that read no result drew none and is worse): the ids follow from the seed, so the run is another run of that seed and says nothing of the group against the one expected, neither better nor worse
changedneither: the run stands where the one expected did, in an outcome that differs all the same, such as in the seconds of its clock

compare exits 0 when every run came out as expected and the sweep has a run for each outcome expected, 1 when not, and 2 when the sweep or the file cannot be read, the file holds outcomes without the ids and the fields of a grow step, or a run was not in one process. It runs with python3: the flake’s app adds --one-process, which compare does not take.

tools/sim/expected/ holds the outcomes of the scenarios CI sweeps at the revision of logos-chat that Cargo.toml pins, and CI sweeps each as many runs as its file holds, from seed 0: two of each 50-epochs-by-saro-waku-loss- file, three of each grow-waku- one. compare --write writes a sweep’s outcomes to the file instead: a change that moves how a run comes out has its outcomes written, and the file’s diff shows the change.

The four 50-epochs-by-saro-waku-loss- files measure how many epochs a group of 51 lasts as one group. Each is 50-epochs-waku-loss.json at no loss, 0.1%, 1% or 5% of the frames each member receives, Welcomes too, with a grow step in place of its seat and post steps (see A group that grows): saro alone adds, one member a round, toward epoch 50, and branches is 51, one for each member, so that a run goes on past any split and the forks it counts are those of fifty epochs. A lost Welcome costs the run one member, who never joined, where one stops a run of 50-epochs-waku-loss.json (see With frames lost). At no loss a fork is the code’s, not the network’s.

A group that grows

Section titled “A group that grows”

A grow step has the runner add members in rounds. Each round draws one to adders members from the seed, and each adds the next member at once, on whatever branch it is on; with by in place of adders, that member alone adds, one a round. The states the members hold form lines: the creator’s first is on the trunk, and where a state has two after it, the one more members hold or have gone past carries the line on and each other starts a branch. A branch off the trunk is a main branch, and one off any other branch a sub-branch. The step ends when the trunk holds epochs, when the trunk and the main branches are branches or more, when every member is seated, or when no member can be drawn. With size, an adder whose add would take the group above it first removes the member seated longest ago.

A grow expects no outcome: how far the group gets before it parts is what it measures. Its run is not checked and writes no expect.json, and it goes as expected when the runner did the step; compare is what holds it to an outcome. After the tables run.txt says how the grow ended, what its rounds came to, and each line. The end of the first run of the sweep above:

A member falls behind when it comes out of a round holding a state another member has gone past, and is behind at the end when it still does. never joined counts the members added that never held the group.

One process, the same run every time

Section titled “One process, the same run every time”

On Linux a scenario and its seeds give one run, whenever and wherever it is made. harness-run stands in for libc’s getrandom, with a generator seeded by the scenario’s seed, and for clock_gettime, so that its time of day is the virtual clock, which starts at 2026-01-01T00:00:00Z; and it runs openmls on one thread. Every random number of the run, the ids of the group and its members among them, follows from the seed, and which commit the group applies follows from the ids. The seed of network fixes what a member’s model does with the n-th frame to reach it. Two runs write the same group.log byte for byte, so a run that changes between two revisions of logos-chat shows what the change did to the group, and nothing else. Elsewhere, as on macOS, the ids come from the OS, and a batch’s seconds can come out a step apart from run to run.

What a network does that one process does not: a member answers a frame in the step it arrives, where over a network the answers come over a second or two. That can make a run in one process take longer. Of fifty members seated ten at a time on the library’s own timers, the ten that the second batch seats never vote on the steward election that batch opens, which is decided at its 30 s timeout, and the third batch is seated after 90 s. Over a network the joiners vote within two seconds, and the batch is seated after 73 to 75 s. How a joiner comes to vote on a proposal made before it joined is not traced. Seated one at a time, as 50-epochs.json seats them, no epoch takes longer than 70.05 s.

Fifty epochs as the module runs them

Section titled “Fifty epochs as the module runs them”

logos-chat-module sets no group timers, so a group in the app runs on the library’s own: a member that has not voted on a proposal within 10 s votes yes (voting_delay), a proposal is decided by its votes or at 30 s (consensus_timeout), every steward makes a commit candidate 60 s after the first approved proposal (commit_batch_window), and the candidates are gathered for up to 30 s before one is chosen (freeze_duration).

A group splits at a commit or holds through it, and each commit opens an epoch, so what a run puts a group through is its epochs: fifty members seated ten at a time are five. Two scenarios take a group through fifty on these timers, saro adding the other fifty members one at a time, and then the last one posts:

  • 50-epochs.json, on a network that loses no frame and holds none;
  • 50-epochs-waku.json, on one that loses none and holds each frame a member receives for a delay Waku relay was measured at.

A third, 50-epochs-waku-loss.json, loses 5% of the frames a member receives on top of Waku’s delays, a rate assumed for want of a measured one (see With frames lost).

The Waku network

Section titled “The Waku network”

The figures come from the simulation the Waku team published as rln-delay-simulations in waku-org/research (#42):

Of the simulation
Nodes1000 nwaku nodes in Shadow, a mesh of 6
Each link100 ms, which the team measured as the average of the live network; 83 Mbit/s down and 38 Mbit/s up
Packets lostnone: each of its 10 messages reached all 999 other nodes
RLN150 ms to make a proof, and 12 ms to check one at each node
Its 10 KB messages, less the first, as the team reads them8991 arrivals: 263 ms the fastest, 507.6 ms the mean, 518 ms the median, 627 ms 95 of 100, 673 ms the slowest

50-epochs-waku.json gives the fifty-one members those arrivals’ quantiles at the middles of 51 equal slices, from 284 to 644 ms, and saro, which creates the group, the median; tools/sim/README.md says which member has which. Two things it leaves out: no measured rate of loss on the live network was found, so the model loses nothing, and a member’s delay is the same for every frame it receives, where on Waku it changes from sender to sender and from message to message.

What they gave

Section titled “What they gave”

An epoch is the seconds from the creator’s add to every member holding the new roster; a post is the seconds until each of the 50 others read it. The run CI makes, seed 0, at the revision chat-sim pins:

ScenarioThe clock at the endEpoch 1Epochs 2 to 50Post, median and worst
50-epochs.json3494.75 s60.0 s70.0 to 70.05 s0 and 0 s
50-epochs-waku.json3627.34 s60.6 s71.75 to 72.95 s0.55 and 0.65 s

Each took about 20 s of wall time on a machine of 16 cores.

  • Fifty epochs take an hour, and the timers are most of it. An epoch after the first takes 70 s, the members’ 10 s to vote and the 60 s window. The first, added while the creator is the group’s only member, takes the window alone. Waku’s delays add 0.6 to 2.95 s to an epoch, and put a post’s reading at the reader’s delay, to the next step of the clock.
  • A seed gives one run. From seed to seed the ids of the group and its members change, and with them which commit the group applies. CI runs seed 0 of both on every push, and Reports shows what they gave.

chat-cli and the local-network branch

Section titled “chat-cli and the local-network branch”

tools/sim can also run a headless chat-cli process for each member, in place of the runner. chat-cli builds on logos-chat changes that the revision chat-sim pins does not hold, so it lives on the local-network branch, pinned to logos-chat’s feat/local-network, with the image a run in containers needs:

RigFlagMembersFor
Local network--chat-cli PATHa chat-cli each, with a delivery node of its own on a network that holds the run’s nodes and no other, and a mock registrythe real network stack, measured up to fifty members on one machine
Containers--image IMAGEthe same, each in a container of its own, on a wire that delays, jitters and loses what it sends (wire)the same over a lossy wire, on Linux or a Mac
Fleet--chat-cli PATH, and preset in the scenariochat-cli peers on logos.testthe public fleet; not reproducible

That branch’s flake adds the apps groupv2-simulation-processes and groupv2-simulation-containers (Linux) beside groupv2-simulation, and its CI runs three.json over a local network, and three.json and lossy-wire.json in containers. Over a network a seed does not make a run again: each chat-cli draws its ids from the OS, and with them which commit applies. tools/sim/README.md covers each rig, what it needs and what it prints.
