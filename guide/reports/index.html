Reports

CI runs on every push to master and on every pull request to master. Two of its jobs run simulations in one process, and a third publishes what they came to beside this guide, under reports: a page for master, and one for each open pull request. A pull request’s simulations run on its head commit, not on its merge into master.

JobRuns
Sim in one process50-epochs.json and 50-epochs-waku.json, once each
Sim held to what is expectedfor each file in tools/sim/expected/, a sweep of the scenario of that name in tools/sim/scenarios/, as many runs as the file holds outcomes, held by tools/sim compare to the file
Publish the report to GitHub Pagesthe report of the CI run, from the text the two jobs upload

The report is published when a simulation job fails as well: that is the run whose report is wanted most. The output of each compare is also in the summary of its job on the CI run.

Every hour, measure-main.yml starts simulate.yml’s main suite at logos-chat main’s tip: seeds 0 to 19 of grow-waku-loss-0, -0.5, -1 and -5 and of their -groupv3 copies. It starts nothing when the tip already has its point on the site, logos-chat/main/<tip>/<measurement>/point.json, at the chat-sim commit a run measures (see logos-chat’s runs), or when a run of main at the tip is queued or in progress. A run of another suite does not hold it back: simulate.yml cancels a run only for a newer one of the same suite at the same revision or pull request. A tip with a point at an older measurement only is run again: what changed in chat-sim is the reason. A run of main at the tip that ended at the measurement without its point holds the tip back too: the next would fail where it failed, so the summary of the hourly run links it, and the tip runs again when it is started by hand. A run of main handed a pr holds the tip back neither going nor ended: it ran at the pull request’s head and keeps no point, and a run started at the tip does not cancel it. Nor does a run of another branch than chat-sim’s default that ended: it keeps no point either.

Once each Sunday, in UTC, measure-main.yml starts the long suite at the tip as well: the two scenarios of fifty epochs once each, and each scenario tools/sim/expected/ holds but the goal’s on either group, as many runs as it holds outcomes, held to them. The first hourly run of the day that finds no run of long handed no pr created that day, queued, in progress or ended, starts it, unless the tip has its long run on the site at the measurement, logos-chat/long/<tip>/<measurement>/long.json, or a run of long is queued or in progress. An hourly run that cannot list the runs created that day starts no long, and main as it would. A run of long that failed is not started again that day: the summary of each later hourly run links it, and it runs again when it is started by hand or on the next Sunday. A run of long takes about three hours: its longest job sweeps grow-waku-size-50.json, whose three runs took 2 h 49 min on a CI run of master.

As expected

Section titled “As expected”

A run in one process is the same run every time from its seeds, on Linux, so a run that comes out other than before was changed by a revision of logos-chat or of chat-sim. tools/sim/expected/ holds, for each scenario CI sweeps, what each of its runs came to at the revision of logos-chat that chat-sim pins in Cargo.toml: the seeds, the ids of the group and of its members, the verdict, the members at the tip of those seated, the seconds of the virtual clock, how the run came out and what stopped its steps, and of a grow step how far the trunk got and how many ended off it. CI sweeps each scenario as many runs as its file holds, from seed 0: two of each 50-epochs-by-saro-waku-loss- file, three of each grow-waku- one. compare holds each run of the sweep to the outcome expected of it, and names each change by where the run stands against it, in the order Simulations gives:

ChangeMeans
samethe outcome is the one expected
betterthe run stands higher than the one expected
worsethe run stands lower
re-rolledboth runs drew ids, and the run drew others than the one expected, the group’s or the members’, so it is another run of that seed and neither better nor worse; a run that read no result drew none and is worse
changedneither: the run stands where the one expected did, in an outcome that differs all the same, such as in the seconds of its clock

A scenario is as expected when every run is same and the sweep has a run for each outcome expected. A change that moves how a run comes out has its outcomes written with python3 tools/sim compare --write EXPECTED OUT, and the file’s diff shows the change.

Why a run repeats

Section titled “Why a run repeats”

On Linux, harness-run stands in for libc’s getrandom with a generator seeded by the scenario’s seed, and for clock_gettime with the virtual clock, and runs openmls on one thread. Every random number of a run, the ids of the group and its members among them, follows from the seed, and which commit the group applies follows from the ids. The seed of network fixes what each member’s model does with each frame. Two runs of one scenario write the same group.log byte for byte. CI runs on Linux. On macOS the ids come from the OS, and a run can come out otherwise from one time to the next.

logos-chat’s runs

Section titled “logos-chat’s runs”

The workflow simulate.yml runs chat-sim at a logos-chat revision it is handed, and its publish job keeps the runs of three of its suites under logos-chat/ of the site: those of main, seeds 0 to 19 of grow-waku-loss-0, -0.5, -1 and -5 and of their -groupv3 copies at a commit of logos-chat’s main, as a point of main, those of pr, seeds 0 to 2 of the lossy ones, three a group, at a logos-chat pull request’s head and at its base, and those of long at a commit of logos-chat’s main, held to what is expected, as a long run. A pull request’s run keeps the matrix tools/sim matrix wrote of the runs and a copy of each scenario file it ran, a point the matrix’s cells and summary, and a long run what each scenario came to and the output of each compare, and each keeps each run’s run.txt, report.txt and run.json, or, of a job that could not build chat-sim, the build’s log, build.log, which the job uploads beside each run’s unbuilt marker. A run’s report.json, ten times the rest, stays in the workflow run’s artifacts. Each has a page drawn from what it keeps, and the comment links it. A pull request’s run also has a page for each of its runs and, where a run moved, a picture of the runs that moved, which its comment shows (see The pages of logos-chat’s runs).

A pr run whose base has its point on gh-pages at the measurement runs nothing at the base: a point’s seeds 0 to 2 are runs 1 to 3 of its sweeps, the runs a pull request asks of the base, so the point’s cells stand in for the base’s, outcomes and ids as the point holds them. A point at another measurement never stands in, and nor does one that has no outcome at one of those runs, as where its job uploaded nothing, or one the plan cannot read: the jobs at the base run them, and a warning on the run says why. When a point stands in, the matrix names it as base_point, and the pull request’s directory holds no base/: the point’s own directory holds those runs’ text while it keeps it. The comment places the head’s runs among main’s twenty seeds of each group’s rate at the point at the base, or else at the newest point at the measurement of the base’s hundred newest commits that logos-chat’s commits API lists, passing over one the plan cannot read, with a warning that says why. The matrix holds that point as spread. A run of the head stands within main’s seeds when its epochs without a fork, the first fork’s or else the trunk’s, are from the lowest of those seeds’ to the highest. Each group’s line in the comment says how many of its runs that moved stand beyond them. The title of a re-rolled verdict says how many re-rolled runs fell below the lowest. The trees of the runs draw main’s seeds as a grey band over their epochs. With no such point, the comment says nothing of main’s seeds, and the trees have no band. The same goes for a rate the point holds no runs of, and for its group’s line.

The measurement is the newest chat-sim commit that touches what a run measures: crates/, Cargo.toml, Cargo.lock, .cargo/, rust-toolchain.toml, flake.nix, flake.lock, tools/forks/forks/, tools/sim/sim/ or tools/sim/scenarios/. A commit to the guide or to the pages moves no point, and one that moves the measurement gives a logos-chat commit a point of its own beside the one before.

A point.json holds what a page of the point draws:

FieldHolds

A point that names no group, in its cells or its summary, holds GroupV2’s runs alone, and is read and drawn as GroupV2’s. A point of an earlier measurement may not count the members that never joined, in its cells or its summary, nor hold a first fork, lines off the trunk or members seated in its summary, and is read as it was written. So are the cells and the spread of a pull request’s matrix, and the runs of a long.json, of an earlier measurement.

A long.json holds what the long run’s page draws:

FieldHolds
logos_chat, measurement, chat_sim, time, run_url, run_numberas a point.json holds them
scenarioseach scenario of the suite, in the order it runs them: its name as scenario; as compare, its verdict by the status compare exited with, as expected, not as expected or no outcome, and the line it ended with as counted, or null where it did not run, as for a scenario chat-sim holds no outcome of; and its runs, each its number as run, its seed, that of the scenario’s file plus the run’s number less one, whether its job could not build chat-sim as unbuilt, and its outcome as compare --write writes one, or null

The points are in the order of their workflow runs’ numbers, which GitHub gives in the order the runs were started and a re-run keeps. A point follows the point of the site of the highest run number below its own but the one of its own commit and measurement, and is refused unless logos-chat’s compare API says its commit is ahead of that point’s, or is that commit. A point, a long run and a pull request’s directory are those of the newest run to publish them, by run number: a publish from an older run is kept out, and a re-run replaces what was there whole. Only a run of chat-sim’s default branch keeps a point or a long run, and none keeps one whose jobs read no run at the revision, built or not, as when logos-chat has no such commit. A long run handed a base holds its runs to the base’s, not to what is expected, and a main or long run handed a pr ran at the pull request’s head, not at a commit of main: neither is kept. A pull request’s directory goes once the pull request is no longer open: the weekly run of Prune Pages removes each logos-chat/pr-N/ whose number logos-chat’s pulls API does not list among its open pull requests, and a dispatch of Prune Pages handed a pr removes that pull request’s alone.

The newest eleven points by run number keep their runs’ text: once a point is written, the runs’ text of each point older than those is removed, and its point.json stays. A point takes about 30 MB while it keeps its text, 13.4 MB of it each group’s runs and 2.9 MB its page, and Pages holds a site of 1 GB. The newest fifteen long runs keep their text, their runs’ and their compare output, and each older one its long.json alone: a long run takes about 10 MB while it keeps its text, 7 MB of it the three runs of grow-waku-size-50 and 1 MB its page, so the eleven points and the fifteen long runs take under half the site. Every publish is a commit on gh-pages, so the weekly run of Prune Pages also rewrites the branch as one commit of its tree as it stands, and the text a point or a long run lets go leaves the branch’s history too.

The comment and the check

Section titled “The comment and the check”

A pr run of simulate.yml handed a pr posts its comment on that logos-chat pull request as chat-sim[bot], the GitHub App chat-sim: it edits the App’s oldest comment there, or writes one where the App has none, so a pull request holds one comment of chat-sim’s. A pr run handed check_run, the id of a check run the App made on logos-chat, moves that check to in progress once its runs are planned, with the workflow run as its details and the runs at the head as its title, 18 runs in progress, and completes it once the comment is posted, with the comment as its summary and the pull request’s report page as its details, or the workflow run where the report has no address.

The comment takes one of four shapes:

WhereThe comment
chat-sim did not build at the headthe verdict line, chat-sim does not build against this commit, with the head, its merge base where there is one, and the links to the report and the run; then that the build’s errors are on the report page, or in the run where the report has no address
no pair of runs was compared, as with no basethe verdict line alone: chat-sim: and the check’s title, then the head, its merge base where there is one, and the links
every run is sameone line: Nothing moved, how many runs of which groups at the head replayed the merge base exactly, or main’s run of it where main’s point stood in, and the links to the report and the run
any othera line for each group; where a run moved, the picture of the runs that moved; the links; and with the picture, how to read the trees

A group’s line, GroupV2’s first, holds in turn:

PartSays
The markof what the line leads with, the first of these: ⚫ no outcome at the head, 🔴 worse, 🟢 better, 🟡 changed, 🔁 re-rolled, ⚪ same, ⚫ not compared
In boldthe group, how many of its runs had no outcome at the head, and how many came out worse, better or changed, such as GroupV3: worse in 2 runs, better in 1; where none did, the first of re-rolled, the same and not compared that its runs have, such as re-rolled in 6 runs or same in 8 of 9 runs
Main’s seedswhere a run moved and the matrix holds main’s seeds of each of the group’s rates, how many of those runs stand beyond them: all within main's 20 seeds, or 1 beyond main's 20 seeds
The resthow many runs each of the rest has, the same last, such as · 1 not compared, 6 same

Where a run moved and the report has an address, the picture of the runs that moved follows the lines. It draws each such run’s tree at the head over the base’s, as the report page draws them (see The pages of logos-chat’s runs). Its source is moved-<revision>.svg beside the report, and moved-<revision>-dark.svg for a reader whose theme is dark. Its name holds the revision, since GitHub’s image proxy keeps a picture it has fetched once. Its alt text names each run and its change. Under it, Open a run: links the page of each of those runs. The links to the report and the run follow, with the head and the merge base. A fold, How to read the trees, closes a comment with the picture. It says what a tree draws, what the grey band of main’s seeds is where the matrix holds those seeds, and that main’s seeds after the merge are the measurement.

Each group has a verdict of its own in the check, over its runs alone, and its own conclusion and title:

The verdictConclusionA group’s title
sameneutralsame as its base, 9 of 9 runs
bettersuccessbetter in 1 of 9 runs
worsefailureworse in 2 of 9 runs
hintneutralworse in 1 of 9 runs, a hint
mixedneutralmixed: 1 better, 1 worse of 9

The check’s title is each group’s after the group’s name, GroupV2’s first: GroupV2 same as its base, 9 of 9 runs; GroupV3 worse in 2 of 9 runs. Its conclusion is a failure where a group’s is, else a success where a group’s is, else neutral, so that one group’s runs standing higher do not hide the other’s standing lower. Where every group’s verdict is unbuilt, or every group’s no-base, the title says it once.

re-rolled’s title says how many runs fell below main’s worst seed where the run has main’s spread to place them among, and stops before the semicolon where it has none. no-base’s title is does not build at the base, no comparison where chat-sim did not build at the base, and no outcome at the base, no comparison where no run at the base has one.

With chat-sim’s repository variable CHAT_SIM_CHECK_REQUIRED set to true, for when the check is made required on logos-chat, a head chat-sim does not build at, or a run with no outcome at the head, fails it; any value but true or false fails the post job before the check completes. no-base stays neutral either way: what it lacks is the base’s, which the pull request cannot give.

The comment job writes the comment, and the post job posts it and completes the check. The post job runs after the publish job, whatever publish came to, so that the check is completed all the same. Where the comment shows a picture, the post job first waits for the Pages site to build what publish pushed: every 10 seconds it asks GitHub’s API for the site’s builds, until the build of that push, or of a later one, is done, for up to ten minutes. It never asks for the picture before then, since the site’s cache keeps a 404 it answered for a while, and would serve it to the comment’s readers too. Where publish pushed nothing, as gh-pages held the run already, it does not wait. Where publish did not succeed, or the site has not built the push in ten minutes, a warning on the run says so, and the comment goes out all the same, its picture perhaps missing. Where the comment shows no picture, the post job does not wait: until Pages serves what publish pushed, about a minute later, the comment’s link to the report opens the page of the pull request’s previous run, or no page yet on its first.

The plan job and the post job each mint a token of their own with actions/create-github-app-token, for logos-chat alone and the permissions their steps need, from the repository variable CHAT_SIM_APP_CLIENT_ID and the repository secret CHAT_SIM_APP_PRIVATE_KEY. The run, comment and publish jobs hold none, and no job hands its token to another. Without the variable or the secret, each says so on the run and posts nothing, and the comment is in the run’s summary alone. A run that is cancelled leaves the check in progress. So does one whose comment job failed, or whose post job failed before it completed the check, until that job runs again.

The pages of logos-chat’s runs

Section titled “The pages of logos-chat’s runs”

The publish job draws the page of each run it keeps, index.html in its directory, from what it keeps there. The comment links it: a pr run’s for a pull request, a main run’s point, and a long run’s page, where the publish job keeps one. A pull request’s comment also links the page of each run that moved.

The report of a pull request’s run, logos-chat/pr-N/:

The treesof each group, under its name, GroupV2 first, and a line that says what its scenarios share that the others do not, such as its timers, and links the copy of each scenario’s file the run keeps, with what that file alone says; then a row a rate and a column a seed, each row headed by its rate and the epochs at which main’s seeds of it first forked, such as main 3 to 19. Each run shows the head’s tree over the base’s on the grey band of main’s seeds, each tree with a ring that counts its members that never joined, where any did. Above them it says where the head’s run first forked, or how its trunk ended. A run that moved also says what the base’s run had, and is outlined in its change’s colour. One that was re-rolled, or where a side did not build, is dashed. Each run links its page
How to read thema paragraph on the trees, and a link to this section of the guide

A tree is drawn from the grow of the run’s run.json (see A group that grows), left to right by epoch from 0 to 50, the goal. The trunk is the top line. Each other line leaves the line it forked from at the epoch it forked at, drops to its row and runs to the epoch it reached, with a dot at its tip. The more members a line ended with, the thicker it is drawn, by the square root of its members against the most of any line drawn with it. Under each line come the lines that left it, the latest to leave first, each followed by the lines that left it in turn, so that no drop crosses a line. A line’s hover text says which line it is, the line it left, its members and its epochs. The base’s run is the one in base/, or main’s point’s while the point keeps its text. A run whose run.json holds no such lineage, as one of an earlier measurement, or whose text the site does not keep, is sketched from how it came out: its trunk dashed to the trunk’s epoch, and a mark down from the epoch of its first fork. The base’s run of a re-rolled run is not drawn, since it drew other ids. A side with no outcome says that it does not build or came to none.

The page of each run, logos-chat/pr-N/head/<scenario>/<run>/, beside the head’s text:

Over main

Section titled “Over main”

Over main draws the points of main, the oldest at the left, in the order of their run numbers. The publish job draws it again from every point.json of the site once it has written a point or a long run, and leaves out, with a warning, a point.json it cannot read. Above the charts it links the page of the newest long run by run number, and draws nothing of it: the charts are of main’s points alone. It lives beside this guide and not in it, since a publish of the guide replaces guide/ whole. Every number it draws is one a point.json holds. Each chart draws GroupV2 and GroupV3 apart, each under its name, GroupV2 first, and a group from the first point that ran it. A rate is a group’s loss, so a scenario renamed at the same loss goes on as its line, and each rate of a group has a blue of its own, the heavier the loss the darker. The rates drawn of a group are those of the newest point that ran it, so a rate main no longer runs leaves the charts. A point that names no group is GroupV2’s.
